# Base Wars - code map

One authoritative **server** executable and one **client** executable (C++23, EnTT, Raylib, Steamworks). No other targets.

```
CMakeLists.txt, CMakePresets.json, .clang-format
cmake/        Compiler, Dependencies (raylib, EnTT), Steamworks (mandatory SDK), Assets, Targets, WriteClientConfig
config/       server.cfg  - documented server tuning, copied next to the server executable
assets/       art, shaders, Tiled UI maps (assets/ui, generated by tools/gen_ui_maps.py)
src/common/   KindDefs.hpp (the kind registry: KINDS table, KT_* tags), Shared.hpp (enums, protocol Msg) + WorldGen / Placement / Serialization,
              Progression.hpp (Town Hall gates, level/cost/time curves), ServerConfig (config/server.cfg loader)
src/components/  data-only EnTT components (server side)
src/networking/  SteamServerNet / SteamClientNet (Steam Networking Sockets), SteamClient (login/friends), ServerBrowser
src/server/   World (shared server state + entity helpers), ServerMain (main + tick loop)
src/systems/  one class per server system, all taking World& and Systems& (see Systems.hpp)
src/client/   App (frame loop), Session, PacketHandler, Commands, Input, Placement, ClientWorld, TestHooks, Settings
src/rendering/  renderers (terrain, water, buildings, units, ships, effects, post-fx, minimap), Assets, Bars, Sprites
src/ui/       widgets (CostRow, tabs, sliders, arrows) and panels (Hud, BuildMenu, ContextPanel, TrainingPanel = Archery,
              TownHallWindow(+Tabs), SocialMenu, Chat, PauseMenu, MainMenu, BigMap, ShipPanel)
```

Headers sit beside their `.cpp`. No `.inc` files. Rule of thumb: files stay under ~600 lines.

## Build

* Requires the Steamworks SDK in `third_party/steamworks` (folder containing `public/steam/steam_api.h`; git-ignored, not redistributable)
  or `-DSTEAMWORKS_SDK_DIR=<path>` / `STEAMWORKS_SDK` env var. Configure fails without it.
* `cmake --preset release && cmake --build build/release`. The post-build steps copy `steam_api`, `steam_appid.txt` (480), `config/server.cfg`
  (server), a `config.txt` and a link/copy of `assets/` (client) next to the executables. `compile_commands.json` is exported.

## Networking

* Steam GameServer + Steam Networking Sockets only (no ENet, no peer-to-peer). The server opens an IP listen socket (direct connections,
  `IP_AllowWithoutAuth`) and a P2P listen socket (Steam Datagram Relay, reachable by SteamID from the browser without port forwarding).
* `server <port> <seed> <savefile> <name> [--local]`: `--local` skips the Steam backend login/advertising (direct IP only).
  The Steam client must be running on the machine for both executables (`SteamAPI_Init` / `SteamGameServer_Init`).
* Client: `client --connect host:port` joins directly; the menu has Internet / Friends / Direct tabs.
* `BW_NETLOG=1` prints Steam connection state transitions.

## Conventions

* The server is authoritative; the client sends `C_*` commands and renders `S_*` messages.
* Protocol: append new enumerators to the END of the `C_*` / `S_*` group of `Msg` in `Shared.hpp`.
* Savegame: bump `SAVE_MAGIC` (`SaveSystem.hpp`) whenever the layout changes; an older format is moved aside (`.bad`) and a fresh world starts.
  A damaged optional section is skipped; an unreadable mandatory part stops the server instead of overwriting.
* Tuning belongs in `ServerConfig` + `config/server.cfg`, shared gate/cost rules in `Progression.hpp`.
* Windows: never name a variable `near` / `far`.
* Inside the client, `ui::` helpers give UI-scale-aware screen size / mouse position; world code uses the raw raylib calls.
* ECS: components are plain data, behavior lives in systems iterating views, shared singletons live in `registry.ctx()`.
* Code style (Doxygen file headers only, plain `//` why-comments, short lambdas, blank-line grouping, function size) is defined in `CLAUDE.md`; follow it.

## Extending the game

One registry per family; ids (`enum Kind`) are persisted and sent, so append only. A `static_assert` in `KindDefs.hpp` checks that every id has an entry.

* **New building type** (typically 3 files, no `switch` edits):
  1. `src/common/KindDefs.hpp`: append the id at the end of `enum Kind` (before `K_Count`; ids are persisted, never reorder) and add one `KINDS[]` entry
     in the same position: stats and cost, `tags` (`KT_*` behaviour flags), `gate` (Town Hall level and
     counts), `menuSlot` (build menu position and hotkey), `siteNote`. The build menu, context panel, gates and placement checks are generated from it.
  2. `src/rendering/UnitAnims.cpp` (`buildingSprite`): the sprite entry. A procedural look is a `drawXxx` method plus a line in the table of
     `BuildingRenderer::drawerOf()` in `src/rendering/BuildingDrawers.cpp`.
  3. New behaviour: a component in `src/components/` and a system in `src/systems/` (registered in `Systems.hpp`); per-instance components are attached from the
     `KindFactory` table in `src/systems/KindFactories.cpp`.
* **New unit / NPC type**: the same `KINDS[]` entry (`trainedAt` = bit mask of training buildings, `archeryLevel`, `thLevel`, `trainSeconds`, `role` / `blurb`),
  animations in `src/rendering/UnitAnims.cpp` (`animTable()` / `fireTable()`), optional `UnitRenderer::drawerOf()` entry (`src/rendering/UnitRenderer.cpp`), optional
  `KindFactory` hooks (`attach`, `onTrained`) for components such as `Wander` or `Healer`.
* **New ship type:** same as units (T14 replaces the `SHIP_*` arrays in `Shared.hpp` with entries here).
* **New effect type:** add an `EffectType`, then one entry in `src/rendering/FxDrawers.cpp`.
* **New behaviour flag:** add a `KindTag` in `KindDefs.hpp` and test it with `hasTag(kind, KT_*)`; never compare kinds in a system or UI file.
* **Draw queue rule:** renderers enqueue `DrawItem{sortY, callable}`. The callable calls one named method and contains no logic.
* **Never** add a per-type `switch` / `if` chain in a system or UI file; extend the table or add a component and system instead.
